## Methodology (must match what the UI states)

Sector score = (`ratio_breaches` × 3 + `severe_ewi` × 4 + `adverse_assessments` × 5
+ `group_risk_signals` × 3 + `open_actions` × 2) ÷ max(entities in sector, 1).

| Band | Rule |
| --- | --- |
| CRITICAL | score ≥ 8 |
| HIGH | score ≥ 4 |
| MEDIUM | score ≥ 1.5 |
| LOW | score > 0 |
| INSUFFICIENT_DATA | no evidence rows in any component |

Component definitions:
- `ratio_breaches` — `return_threshold_breaches` with `acknowledged_at IS NULL`, level/risk level high, breach or critical, within the lookback window, joined to the filing entity.
- `severe_ewi` — `prudential_ewi_alerts` with severity high/critical and status still open/acknowledged, within the lookback window.
- `adverse_assessments` — `prudential_assessments` with an overall rating of 4, 5, HIGH, CRITICAL, ADVERSE or UNSATISFACTORY.
- `group_risk_signals` — current `group_risk_scores` banded high/critical for groups with an active member in the sector.
- `open_actions` — `prudential_actions` with severity high/critical and status not closed/cancelled/completed/withdrawn.

## Procedure 1 — heatmap is no longer a conduct proxy

1. Sign in as a prudential supervisor and open the executive supervisory dashboard.
2. Confirm the heatmap's third column is headed **Prudential risk** and shows a band plus a numeric score, with an evidence breakdown column (`br / ewi / asmt / grp / act`).
3. Pick one sector and verify each component number against its own module list (breaches, EWI alerts, assessments, group risk, supervisory actions).
4. Recompute the score by hand with the weights above and confirm the band matches the table.

Record: sector, five component counts, hand-computed score, band shown.

## Procedure 2 — insufficient data is never reported as low risk

1. Choose a sector with no prudential evidence.
2. Confirm the cell reads **insufficient data** in a neutral tone, not "low".
3. Confirm no drill-through link is offered for that sector's prudential cell.

## Procedure 3 — permission denial

1. Sign in as a user without `prudential_supervision.view` (for example a conduct-only analyst).
2. Open the executive dashboard. The complaints column still renders; the prudential column reads *insufficient data* and the footnote states prudential scoring is hidden.
3. Confirm the network response for `prudential_sector_risk` is a permission error and that no component counts appear anywhere in the payload.

## Procedure 4 — KPI reconciliation on live data

For each of licensing, F&P, prudential, conduct, investigations, enforcement and SLA:

1. Note the headline number on the dashboard tile.
2. Click through to the drilldown list and note its total.
3. Export the drilldown and count the rows.
4. All three must be identical. Record any mismatch with the tile name, the three numbers, and the filter set in play.

## Procedure 5 — governed report export

1. Run any report with an entity filter and a period filter.
2. Export as CSV: the file begins with `# Report`, `# As-of period`, `# Entity`, `# Regulator / sector`, `# Filters`, `# Generated by`, `# Generated at`, `# Rows` before the header row.
3. Export as XLSX: a second sheet named **Provenance** carries the same fields.
4. Export as PDF: the provenance block is printed under the title.
5. Export as JSON: the payload is `{ provenance, rows }`.
6. Confirm the row count in the provenance block equals the rows visible on screen; if they differ, the export is blocked with "Export blocked".
7. Open the audit export registry and confirm a new row exists for the export with the justification text, the format, the row count, the filter payload and the file hash.

Record: report name, format, provenance row count, on-screen row count, registry row id.
