# RC1 batch 2 — migrations, production safety, cutover hygiene

Status date: 2026-08-23. Scope: §1 fresh install chain, §2 upgrade chain,
§3 environment safety, §4 test-only inventory, §5 production cutover,
§6 secret/credential safety.

## §1 — Fresh install path: CERTIFIED (via squashed baseline)

Replaying the full 1,003-file migration history against an empty database is
**not** a supported install path and cannot be made one: ~200 migrations are
data-coupled (they update or reference rows created out-of-band in the hosted
project — regulator IDs, historic fixtures, seeded config). This is recorded as a
deliberate architectural decision, not an open defect.

The certified install path is therefore:

```
scripts/rc1/db/bootstrap.sql        platform shims (auth/storage/cron schemas, extension stand-ins)
supabase/baseline/                  squashed certified schema (generated by generate-baseline.sh)
supabase/migrations/*               only files newer than the baseline marker
```

`scripts/rc1/db/install-baseline.sh [db] --from <migration>` runs the whole path
on a disposable local cluster and finishes with `scripts/rc1/db/post-checks.sql`.

Result: `VIEWS_FAILED=0`, all RBAC objects/functions present, RLS + grant
post-checks pass, `NOT_VALID_CONSTRAINTS=0` (the last one,
`report_logs_report_run_id_fkey`, had zero orphan rows and is now validated).
`40_functions.sql` is applied twice (`check_function_bodies = off`) because table
DDL references functions (generated columns) while function bodies reference
tables; every statement is `CREATE OR REPLACE`, so the second pass is
authoritative.

## §2 — Upgrade path

`scripts/rc1/db/migration-chain.sh upgrade <cutover-migration>` applies history up
to a cutover point, loads a representative dataset
(`scripts/rc1/db/upgrade-seed.sql`), then applies the remaining migrations and
asserts data survival (`scripts/rc1/db/upgrade-verify.sql`) followed by the shared
structural post-checks. The harness is isolated from the hosted project: every
`PG*` variable is unset and re-pointed at the local cluster before any `psql`
call, and `pg_cron`/`pg_net`/`pgtap` `CREATE EXTENSION` statements are neutralised
because those extensions are not installable in the sandbox.

## §3 — Environment safety: ENFORCED SERVER-SIDE, FAIL CLOSED

New runtime table `public.app_environment_config` (single row) classifies the
deployment as `production` or `non_production`. It is readable by signed-in users
and writable only by `service_role` / deployment tooling (no write policy).

* `public.is_production_environment()` — `STABLE SECURITY DEFINER`, `service_role`
  only. Returns `true` unless a row explicitly says `non_production`, so a missing
  row, an empty table or an unknown value all mean *production*.
* `public.assert_nonproduction(text)` — raises `42501` on production.
* `public.cert_v2_guard_ok()` — now returns `false` when the deployment is
  production, and also when `cert_nonproduction_guard` is absent (previously this
  raised an opaque "relation does not exist"). Every guarded harness function and
  the `cert-v2-user-fixtures` edge function funnel through it, so
  reset / reseed / certification-user provisioning are all denied on production.
* EXECUTE on every non-extension `cert_*` and `rc1_*` function was revoked from
  `PUBLIC`, `anon` and `authenticated`; only `service_role` retains it.

## §4 — Test-only object inventory

See `docs/certification/rc1-test-object-inventory.md`: 8 tables, 57 functions and
the `pgtap` extension (1,074 owned functions) classified `NONPROD_ONLY` /
`TEST_ONLY`; four similarly-named business routines explicitly retained.

## §5 — Production cutover migration

`supabase/migrations/20260823163215_*.sql` drops all inventoried objects and the
`pgtap` extension. It is a **no-op** unless `is_production_environment()` is true,
so it is safe in permanent history, and it is idempotent (verified: second run
produced zero errors).

## §6 — Secret / credential safety: CLEAN

* `src/` contains no service-role key, JWT literal, provider secret or hardcoded
  password; the only `import.meta.env` reads are
  `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID`
  (all publishable) plus `import.meta.env.DEV`.
* `.env` contains only those three publishable values.
* `CERT_V2_DEFAULT_PASSWORD` is read from the environment at runtime in the edge
  function and in the e2e/scripts harnesses; it is never logged, returned or
  persisted.
* Worker/cron endpoints stay behind `_shared/workerAuth.ts` (service key,
  `x-worker-token`, or a single-use database-issued token) with constant-time
  comparison.

## Residual risks

* The install baseline is a generated artefact: regenerate it with
  `scripts/rc1/db/generate-baseline.sh` whenever the certified schema changes,
  otherwise fresh installs drift from the hosted schema.
* Promoting an environment to production requires setting
  `app_environment_config.environment = 'production'` as part of the deployment
  runbook; the default already fails closed if that step is forgotten.
