## Classification rules

Records are classified by **provenance and dependency**, never by display name:

| Classification | Meaning | Action |
|----------------|---------|--------|
| `PURGE_OLD_FIXTURE` | Row belongs to, or depends on, the `CERTIFICATION_DATASET_V1` manifest | Eligible for removal at CLEAN, in dependency order |
| `PURGE_ORPHAN` | Row has no canonical entity/licensee linkage — cannot participate in a supervisory journey | Eligible for removal, individually logged |
| `MANUAL_REVIEW` | No fixture provenance, or auth-linked | **Not** removed without an explicit human decision |
| `KEEP_AUDIT` | Immutable audit / delivery history | Never purged |
| `KEEP_REFERENCE` | Provenance ledger and configuration | Never purged |

## Purge design (not yet executed)

1. CLEAN removes only rows registered in `cert_fixture_objects` with
   `cleanup_policy = 'purge'`, in descending `delete_order` from
   `cert_fixture_object_types`.
2. The legacy V1 dataset is retired in the same order using the manifest as its
   registry; it is registered into the V2 ledger before removal so the deletion
   itself is attributable.
3. `MANUAL_REVIEW` rows are never touched by the harness. They are listed here
   and require an explicit decision before any removal.
4. Audit, compliance-audit and notification-dispatch history is out of scope for
   deletion in every wave.
