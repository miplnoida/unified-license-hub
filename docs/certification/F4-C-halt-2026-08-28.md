## DEF-F4-C-02 — Coordination audit triggers write to non-existent audit columns

**Classification:** PRODUCT_DEFECT (Critical) — coordination readiness dimension
of F4 cannot transition state at all in production.

### Broken objects

| Trigger | Table | Function |
|---|---|---|
| `trg_log_coordination_case_change` | `public.coordination_cases` (UPDATE) | `public.log_coordination_case_change()` |
| `trg_log_coordination_flag_ins` | `public.coordination_flags` (INSERT) | `public.log_coordination_flag_change()` |
| `trg_log_coordination_flag_upd` | `public.coordination_flags` (UPDATE) | `public.log_coordination_flag_change()` |

All three are `SECURITY DEFINER`, `SET search_path = public`, enabled (`tgenabled = 'O'`),
and execute:

```sql
INSERT INTO audit_logs (actor_id, action, entity_type, entity_id, details) ...
```

### Actual `public.audit_logs` columns

```
id, user_id, action, entity_type, entity_id, old_value, new_value, metadata, created_at, user_role
```

`actor_id` and `details` do not exist. There is exactly one `audit_logs`
relation in the database (`public.audit_logs`), so this is not a `search_path`
resolution artifact.

### Canonical production reachability (no fixture involved)

`src/pages/coordination/CoordinationDetail.tsx`

- line 454 — `supabase.from('coordination_participants').insert(...)`
  → `coord_check_clearance()` → `UPDATE coordination_cases SET status='cleared'`
  → `trg_log_coordination_case_change` → **42703**
- line 582 — `supabase.from('coordination_flags').insert(...)`
  → `trg_log_coordination_flag_ins` → **42703**
- line 609 — flag resolve/withdraw update → `trg_log_coordination_flag_upd` → **42703**
- line 231 — case status update → `trg_log_coordination_case_change` → **42703**

`src/pages/coordination/CoordinationList.tsx` line 84 (case create) reaches the
same clearance path through `coord_case_seed_owner()`.

Consequences: no coordination case can be cleared or closed, no coordination
flag can be raised, resolved, or withdrawn. Because a coordination blocker is
one of the seven F4 licensing readiness dimensions, the dimension is
structurally inert — it can only ever fail closed, never clear.

### Required F4-B remediation (not applied under F4-C)

Rewrite both trigger functions to the real audit contract — `user_id` in place
of `actor_id`, `metadata` in place of `details` — keeping the actor as
`auth.uid()` and preserving the existing action keys
(`coordination.case.<status>`, `coordination.flag.raised`,
`coordination.flag.<status>`). No audit requirement is to be weakened: the
actor stays server-derived and the payload stays complete.

Also required in the same F4-B pass: a repository-wide sweep for any other
audit-writing trigger/function using the `actor_id` / `details` column names, so
the category — not the instance — is closed. The census run at halt time found
exactly these two functions.
