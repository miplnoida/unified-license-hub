# Role Management Hardening

_Last updated: 2026-07-21_

Role Management now enforces three invariants — one in the UI, all three in the database. The database is authoritative: even a direct SQL insert against `role_permissions` obeys them.

## 1. Dependent actions require `view` on the same module

Selecting `edit`, `create`, `delete`, `approve`, `reject`, `export`, `download`, `upload`, `import`, `publish`, `archive`, `restore`, or `assign` requires `view` on the same module. The UI auto-adds `view` when the administrator toggles a dependent action on, and refuses to remove `view` while any dependent action is still selected. The database enforces the same rule via the `assert_role_permission_dependencies` BEFORE INSERT trigger on `public.role_permissions` — a direct insert of `edit` without `view` fails with a clear error.

Frontend implementation: `src/lib/rbac/permissionDependencies.ts` — `resolveDependencies()` and `permissionHasDependency()`. These are pure functions used by both `src/pages/admin/RoleManagement.tsx` (interactive checkbox toggling and `handleSave`) and Vitest (`src/test/rbac/permissionDependencies.test.ts`).

Backend implementation: `supabase/migrations/20260721061053_role_management_hardening.sql` — declares `public.get_permission_dependencies()` and `public.permission_has_dependency(text)`, plus the trigger `role_permissions_dependency_check`.

## 2. Orphaned permissions cannot be assigned

A permission is _orphaned_ when it appears nowhere in the enforcement surface — no menu, no route, no button, no RLS policy, no RPC, no storage policy, no report. The `permissions.enforced` boolean column marks which catalogued permissions are actually wired up. The BEFORE INSERT trigger `role_permissions_reject_orphaned` on `public.role_permissions` rejects any row whose permission has `enforced = false`.

Administrators update `permissions.enforced` when a surface is added or retired — never in application code paths, only through a migration that also lands the enforcement surface.

## 3. Permission Coverage Matrix

The matrix is the source of truth for _where_ each permission is enforced. It is generated by scanning source files and SQL migrations:

```
bunx tsx scripts/generate-permission-coverage.ts
```

Outputs (regenerate before releases, and any time a permission is added, removed, or re-wired):

- `docs/rbac/permission-coverage.md` — human-readable table per module, with badges.
- `docs/rbac/permission-coverage.csv` — spreadsheet-friendly, one row per permission.
- `docs/rbac/permission-coverage.json` — the artifact consumed by the admin UI at `/admin/permission-coverage`.

### Surfaces scanned

| Surface | Signal |
| --- | --- |
| Menu | `module: '<key>'` entries in `src/config/navigation.tsx` — always mapped to `<module>.view`. |
| Route | `<M module="…">` and `<ModuleRoute module="…">` in `src/routes/**` — mapped to `<module>.view`. |
| Button | `<PermissionGate module="…" action="…">`, `<GuardedButton module="…" action="…">`, and `data-rbac="module.action"` markers across `src/pages/**` and `src/components/**`. |
| RLS | `has_permission(user, 'module', 'action')` inside a `CREATE POLICY` body whose `ON` clause is _not_ `storage.objects`. |
| RPC | `has_permission(...)` inside a `CREATE FUNCTION` / `CREATE OR REPLACE FUNCTION` body. |
| Storage | `has_permission(...)` inside a `CREATE POLICY ... ON storage.objects`. |
| Report | Every file under `src/pages/reports/**` implicitly consumes `report_management.view`, plus any explicit `data-rbac` markers. |

### Coverage classes

- **Enforced** — appears in at least one UI surface **and** at least one backend surface. Safe.
- **Backend only** — enforced server-side but the UI has no way to invoke it. Fine for programmatic paths (RPCs / scheduled jobs), otherwise indicates a missing button.
- **UI only** — a menu / route / button uses it but no policy or RPC enforces it. **This is a red flag: frontend gating is not security.** Add an RLS policy or RPC gate.
- **Orphaned** — used nowhere. Cannot be assigned (server rejects).

### Admin view

`/admin/permission-coverage` renders the JSON as a searchable, filterable table. Access is gated by `role_management.view`.
