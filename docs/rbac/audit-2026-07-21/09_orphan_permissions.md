# 09 · Orphan Permission Report

Definition: a catalog row (`permissions.module` × `permissions.name`) is **orphaned** when the
coverage scanner finds **zero** enforcement surfaces (menu, route, button, RLS, RPC, storage, report).

## Numbers

| Metric | Value |
|--------|-------|
| Catalog rows | 123 |
| Enforced somewhere | 24 |
| **Orphaned** | **99** |

Full list is regenerated by:

```
bunx tsx scripts/generate-permission-coverage.ts
```

and lands in [`docs/rbac/permission-coverage.md`](../permission-coverage.md) / `.csv` / `.json`.

## Why so many

The catalog was populated ahead of enforcement. The Role-Management hardening migration
(`20260721061053_role_management_hardening.sql`) added the `enforced` column and prevents assigning
an orphan permission to a role — but the rows still exist for future wiring.

## Recommendation

1. Add an `expected_surface` column to `permissions` (values: `menu`, `route`, `button`, `rls`, `rpc`,
   `storage`, `report`) so the CI check can fail *specifically* on missing surfaces rather than "any"
   surface.
2. Prioritise enforcement in this order:
   - `<module>.view` for every module that has a route — RLS + menu already exist for most.
   - `<module>.edit` / `.approve` / `.delete` — attach to the RPCs that persist changes.
   - `<module>.export` — attach to the report runner and edge exports.
3. Delete any catalog row that has no product intent after the wave completes.

Orphans do **not** create a vulnerability by themselves (they are unassignable), but they inflate
the surface area of the catalog and make coverage reports misleading.
