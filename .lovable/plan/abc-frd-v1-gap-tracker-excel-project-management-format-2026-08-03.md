# ABC_FRD_v1 Gap Tracker (Excel, project-management format)

No application code changes. The only output is a downloadable Excel workbook shared in chat.

## What the FRD contains (verified by reading the file)

`ABC_FRD_v1.docx` is a screen-level specification with **100 screen IDs** across 8 modules:

| Module | Code | Screens in FRD |
| --- | --- | --- |
| Admin Console & Configuration | ADM | 14 (FB, WF, RE, RM, SLA, INT) |
| Licensing, Registration & Approvals | LIC | 19 (APP, INT, REV, DEC, LCY, APL) |
| Fit & Proper Assessment | FP | 11 (REG, SCR, ASS, COM, CON) |
| Prudential Supervision | PRU | 11 (ENT, RET, ANA, ASS, EXM, ACT, GRP, PAY) |
| Market Conduct & Consumer Protection | MCS | 26 (POR, CMP, ANA, THM, INV, ENF, SUR, MON) |
| Dashboards, Reporting & Analytics | DASH | 9 (EXE, OPS, ENT, RPT, AI) |
| Audit, Compliance & Governance | AUD | 6 (LOG, LIN, SEC, OVR, EXP) |
| Notifications & Communications | NOT | 3 (CEN, THR, ESC) |

Each screen carries purpose, UI components, business rules, actions, validations, notifications and audit events — so the tracker is built at screen level with sub-item rows where the FRD specifies distinct capabilities inside one screen.

## Workbook: `FRD_Gap_Tracker_v3.xlsx`

Sheets:

1. **Summary** — counts and % complete per module (Done / Partial / Missing / Not in scope), plus overall completion, generated by formula from the tracker sheet.
2. **Tracker** — one row per FRD screen/capability with PM-tracker columns:
   `Item ID | FRD Screen ID | Module | Sub-Module | Requirement (FRD title) | FRD Purpose | Status (Done / Partial / Missing) | % Complete | Evidence in system (route / file / DB object) | Gap detail (what exactly is missing) | Effort (S/M/L) | Priority (P1/P2/P3) | Dependency | Owner | Notes`
3. **Gaps only** — filtered view of Partial + Missing rows, sorted by Priority, for direct sprint planning.
4. **Module rollup** — module-level readiness with the top blocking gaps per module.

## How status is decided (evidence-based, not assumed)

For every screen I verify against the live repository and database before setting status:

- routes in `src/routes/*` and `src/pages/**` for screen existence and role gating,
- hooks/services under `src/hooks/**`, `src/lib/**` for the data behaviour the FRD demands,
- database objects (tables, RPCs, triggers, RLS) via live queries for business rules, notifications and audit events,
- existing verification docs under `docs/verification/**` and `docs/rbac/**` where they already prove behaviour.

Rules: a screen is **Done** only when the screen, its stated business rules, its notifications and its audit events all exist; **Partial** when the screen exists but named FRD capabilities (AI advisory panels, committee voting, thematic reviews, PFMI dashboards, etc.) are absent; **Missing** when there is no route/table backing it. No row is marked Done without concrete evidence recorded in the Evidence column.

## Formatting

Arial throughout, frozen header row, autofilter, colour-coded status (green/amber/red), column widths set for printing, and percentages as real numeric formats so the Summary formulas compute.
