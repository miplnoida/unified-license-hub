# Role Management — Dependency Enforcement + Permission Coverage Matrix

Two coordinated improvements to `RoleManagement`:

1. Enforce that any non-`view` action on a module implies `view` on that module — automatically, or by blocking save.
2. Ship a **Permission Coverage Matrix** that shows, for every permission in the catalog, whether it is actually enforced anywhere (menu, route, button, RLS, RPC, storage, report) and flags orphans. Prevent admins from assigning orphaned permissions.

## Part 1 — Permission dependencies

### Rule set

For every module the following action → prerequisite mapping applies:

```text
edit      requires view
create    requires view
delete    requires view
approve   requires view
reject    requires view
export    requires view
download  requires view
upload    requires view
import    requires view
publish   requires view
archive   requires view
restore   requires view
assign    requires view
```

Anything else is unconstrained. The rule set lives in one file
(`src/lib/rbac/permissionDependencies.ts`) as `{ [action]: prereq[] }`
so it can be extended without touching UI code.

### Enforcement — client

- `resolveDependencies(selectedIds, catalog)` — pure function that
  returns `{ added: string[], violations: {action, module}[] }`.
- Two save modes exposed via a single "Auto-add prerequisites" toggle
  in the role editor (default **on**):
  - **On** — missing prereqs are added silently on save; a small inline
    hint appears while editing ("View will be included automatically").
  - **Off** — save button is disabled and each row with a missing
    prereq gets an inline error ("Requires Returns → view").
- The action-row checkboxes in the module grid render a small "requires
  view" badge whenever a dependent action is checked but `view` is not.

### Enforcement — server

A `BEFORE INSERT` trigger on `role_permissions` calls a new
`public.assert_role_permission_dependencies(role_id, permission_id)`
function that:

- Looks up the permission's `(module, name)`.
- If `name` is in the dependency map, verifies the role also holds the
  corresponding prerequisite permission (present-in-set OR being
  inserted in the same statement, using a `pg_trigger_depth() = 0` +
  deferred constraint pattern).
- Raises `dependency_missing` (`SQLSTATE 22023`) with a clear message
  if not.

This blocks direct DB writes (RPCs, migrations, service-role callers)
from creating invalid combinations even if the UI is bypassed.

### Tests

- `src/test/rbac/permissionDependencies.test.ts` — pure-function unit
  tests: adds missing view, reports violations, no-ops on view alone,
  handles multiple modules in one edit, respects super_admin (no
  auto-add needed there).
- `supabase/tests/rbac/10_permission_dependencies.sql` — pgTAP: seeds a
  role, attempts to grant `returns_management.edit` without
  `returns_management.view`, expects `dependency_missing`; then grants
  view + edit atomically and expects success; then attempts to revoke
  view while edit remains and expects failure.

## Part 2 — Permission Coverage Matrix

### Scanner

Extends the existing `src/lib/rbac/audit.ts` scanner into a shared
`src/lib/rbac/coverage.ts`:

```ts
type CoverageRow = {
  module: string;
  action: string;
  menu: { file: string; line: number }[];       // src/config/navigation.tsx entries
  route: { file: string; line: number }[];      // <M module="..."> guards
  button: { file: string; line: number }[];     // PermissionGate / GuardedButton / data-rbac
  rls: { file: string; line: number }[];        // has_permission(...) in supabase/migrations/*.sql
  rpc: { file: string; line: number }[];        // has_permission(...) inside CREATE FUNCTION bodies
  storage: { file: string; line: number }[];    // storage.objects policies referencing the key
  report: { file: string; line: number }[];     // src/pages/reports + reportDefinitions.ts
  orphaned: boolean;                            // true when every list is empty
};
```

Sources walked:

- `src/config/navigation.tsx` — menu
- `src/routes/**` and every `<M module="...">` occurrence — route
- Existing button scan from `audit.ts` (`PermissionGate` /
  `GuardedButton` / `data-rbac`) — button
- `supabase/migrations/**/*.sql` — RLS + RPC + storage: parse
  `has_permission\((?:auth\.uid\(\)|_user_id),\s*'([^']+)',\s*'([^']+)'\)`
  and classify by surrounding SQL context (`CREATE POLICY … ON storage.objects` → storage, `CREATE POLICY …` → rls, `CREATE OR REPLACE FUNCTION …` → rpc).
- `src/pages/reports/reportDefinitions.ts` and `src/pages/reports/**`
  — report.

### Report artifacts

Generated by `scripts/generate-permission-coverage.ts`:

- `docs/rbac/permission-coverage.md` — grouped by module, with an
  emoji + column per surface, orphan section at the top.
- `docs/rbac/permission-coverage.csv` — flat matrix: `module, action, menu, route, button, rls, rpc, storage, report, orphaned, first_reference`.
- `docs/rbac/permission-coverage.json` — machine-readable full detail
  (used by the Role Management UI at build time).

### Vitest floor

`src/test/rbac/permissionCoverage.test.ts`:

- Loads the JSON artifact.
- Asserts every module × action in `permissions` (catalog snapshot
  committed under `src/lib/rbac/catalog.json`, regenerated via a
  script) appears in the matrix.
- Baseline `ORPHAN_ALLOWLIST` set — starts as the current orphan list
  and can only shrink. Anything new fails CI.

### Role Management UI

- New "Coverage" column in the module permission grid renders a small
  badge:
  - `Enforced` (green) — appears somewhere.
  - `UI only` (amber) — button/menu/route but no RLS/RPC/storage.
  - `Backend only` (blue) — RLS/RPC/storage but no UI surface.
  - `Orphaned` (red) — nowhere.
- Orphaned permissions become **unassignable**: checkbox disabled,
  tooltip explains why, and any legacy assignment already on the role
  is shown under the existing "Legacy permissions kept on this role"
  panel with a "Remove orphan" button.
- Save blocks if any orphaned permission remains selected (same error
  channel as dependency violations).
- A "View Coverage Report" link opens
  `/admin/roles/permission-coverage`, a read-only page that renders
  the matrix (grouped by module, with search + module filter + orphan
  filter). No admin-only bypass — gated on
  `role_management.view`.

### Server guard against assigning orphans

`assert_role_permission_dependencies` (from Part 1) also checks a new
`permissions.enforced` boolean:

- New column `public.permissions.enforced boolean NOT NULL DEFAULT true`.
- A migration seeds it by reading the checked-in coverage snapshot.
- Trigger raises `permission_orphaned` on insert when `enforced = false`.
- The Role Management UI reads this column to decide the "disabled"
  state, so client and server agree.

The coverage generator, at CI time, writes an `orphans` list to
`supabase/seed/permission-coverage.sql` that the generator can apply
via a follow-up migration. The migration itself is not auto-applied —
each orphan flip is a reviewed change.

### pgTAP

`supabase/tests/rbac/11_permission_orphan_guard.sql`:

- Flips a test permission's `enforced` to `false`, expects
  `permission_orphaned` on insert into `role_permissions`.
- Flips back to `true`, expects success.

## Non-goals

- No changes to how permissions are named or grouped.
- No auto-deletion of existing role assignments — orphans on existing
  roles are surfaced and offered for removal, never removed silently.
- No changes outside `RoleManagement`, the new coverage page, and the
  two migrations.
