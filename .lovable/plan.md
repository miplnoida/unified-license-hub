# ADM-INT-001 — Rewire business flows through the Integration Manager

## Verified current state (checked this turn)

- `invokeIntegration()` exists at `supabase/functions/_shared/integration/invoke.ts` and is referenced **only** by its own tests and `docs/verification/integrations/03_invocation_service.md`. **No business module calls it.**
- Registration (`register-pre-licensee`, `send-registration-otp`, `verify-registration-otp`) contains no identity/KYC provider step at all — identity validation today is internal only.
- Fit & Proper screening lives in `supabase/functions/fp-screening-run/index.ts` and runs its own internal logic.
- Payment creation/confirmation is simulated client-side (`src/pages/payments/PaymentHistory.tsx`); `verify-and-submit` only reads the `payments` table as a submission gate.
- Licence signing is `sign-license-certificate` + `generate-license-certificate` (internal only). Registry publication surface is `public-registry`.
- No durable retry queue, no dead-letter table, no bypass scanner script.

So this task is exactly rewiring + durable retry/DLQ + guards + executable proof. The registry, adapters, fallback governance and invocation service are untouched except where an operation is missing.

## Delivery order (one group per turn; nothing is claimed closed without green tests plus its report)

### Group C — Durable retry queue + DLQ (items 8, 9)
`integration_retry_queue` and `integration_dead_letter` with the full field list and the seven statuses (`queued`, `processing`, `retry_scheduled`, `succeeded`, `failed`, `cancelled`, `dead_letter`). A claim RPC using `FOR UPDATE SKIP LOCKED` with lease/heartbeat and stale-worker recovery, exponential backoff with jitter, per-integration attempt caps, attempt history, and a hard rule that permanent business rejections are never enqueued. A worker edge function drains the queue re-using the original idempotency fingerprint. Admin UI gains a **Retry Queue / Dead Letter** tab under `/settings/integrations` with search, filters (module, integration, error category, date range), attempt history, redacted request, provider response, source-record and log deep links, Retry Now, Batch Retry, Cancel, Mark Resolved with note, and export. Manual retry requires permission plus justification and writes an audit row.
Deliverables: durable-retry report, DLQ report, idempotency report.

### Group D — Business rewiring (items 1–6)
Each flow calls `invokeIntegration()` first and keeps today's logic as the **governed** fallback, labelled honestly.

- **Registration / identity** → `identity_verification.verify_identity`, invoked after internal validation succeeds, with source module `registration`, business event, registration ID, correlation ID, deterministic idempotency key (registration submission), actor, fallback policy. `real` records provider + reference + externally-verified; `mock` records `mock_verified` and never shows "Externally verified"; `fallback` runs internal validation and records `internally_validated_provider_unavailable` with reason and provider-unverified retained; `blocked` stops with a manual-review state and no fallback. Adverse results never fall back; repeat submissions never duplicate requests.
- **Fit & Proper** → `aml_screening`, `sanctions_screening`, plus `credit_bureau` and `identity_verification` where applicable. One correlation ID per run, distinct idempotency keys per provider operation. Persists provider, execution mode, provider-verified flag, provider reference, subject, date, result, match status, score, safe raw-response reference, correlation ID and log ID on the assessment. AML/sanctions matches, auth/authorization/validation rejections, malformed compliance results and adverse credit stay blocked or go to manual review — fallback only for not-configured, disabled, network, timeout, provider-unavailable, circuit-open — and is labelled `internal_screening_provider_unavailable`, never as third-party screening.
- **Payments** → `payment_gateway` for create, fetch, capture, refund, reconcile and callback, via a governed edge function; the client stops calling the simulator directly. The simulator is reachable only when the connection is explicitly in mock/simulator mode or an approved fallback policy selects it before any real attempt. No fallback after decline, insufficient funds, invalid instrument, auth/fraud rejection, duplicate transaction or refund rejection. Timeout/unknown keeps the payment pending, schedules reconciliation, and never re-issues a new idempotency key. Callbacks are idempotent. Stores provider transaction ID, execution mode, amount/currency, provider status, internal status, correlation ID, idempotency fingerprint, callback event ID, log ID. Existing payment history shape and the submission gate stay intact.
- **Licence signing** → `document_signing` create/fetch/download/void/callback. With no provider the internal certificate remains, marked `internally_generated`, execution mode `fallback` with reason, never "externally signed"; issuance is not rolled back for an optional provider. No fallback after signature rejection, void, signer refusal, invalid document or auth rejection. Callback replay creates no duplicate document or status transition.
- **Registry publication** → `government_registry` (or the configured registry key) for verify/fetch organisation, publish licence, fetch status, process acknowledgement. Internal approval stays separate from external publication; with no provider the external status is `not_configured` / `pending_external_publication`. Registry rejection, duplicate record, invalid data, authorization and mapping failures never become publication success. Retries never duplicate registry records.
- **Existing internal integrations** (AI gateway, SMTP/email, reporting, audit export, platform API, notifications, internal registry APIs): route through `invokeIntegration()` where a connection is registered, otherwise document why the existing dispatcher is already the canonical path. No duplicate wrappers.

Deliverables: business-flow rewiring matrix, call-site matrix, registration/KYC report, F&P report, payment report, e-signing report, registry-publication report.
